## Executive Summary

OpenClaw can integrate with Claude Code and similar coding agents through its **Agent Client Protocol (ACP)** framework. The system provides first-class support for external coding harness agents including Pi, Claude Code, Codex, OpenCode, Gemini CLI, and Kimi. Integration is achieved via the `sessions_spawn` tool with `runtime: "acp"` or through the `/acp` command family.

**Key Finding:** Claude Code integration is supported as a documented use case within OpenClaw's ACP framework.

---

## Key Findings

1. **Native ACP Support**: OpenClaw implements ACP as a first-class runtime for external coding agents.

2. **Multiple Harness Support**: Built-in support for Pi, Claude Code, Codex, OpenCode, Gemini CLI, and Kimi via the `acpx` backend plugin.

3. **Flexible Spawning**: Use `sessions_spawn` with `runtime: "acp"` for one-shot (`mode: "run"`) or persistent (`mode: "session"`) execution.

4. **Thread Binding**: ACP sessions can bind to Discord threads or Telegram topics.

5. **Sandbox Limitations**: ACP sessions run on the host, not in the sandbox—sandboxed sessions cannot spawn ACP agents.

6. **Permission Model**: Non-interactive ACP requires explicit permission configuration via acpx plugin.

## Technical Analysis

### OpenClaw Architecture

OpenClaw is a self-hosted multi-channel gateway connecting chat apps (WhatsApp, Telegram, Discord, iMessage) to AI agents. Key components:
- **Gateway**: Central process managing sessions, routing, channels
- **Agents**: Isolated brains with separate workspaces, auth, session stores
- **Channels**: Adapters for each messaging platform

Each agent has dedicated workspace, state directory, and session store under `~/.openclaw/agents/<agentId>/`.

### Agent Workspace System

Workspace contains: `SOUL.md`, `AGENTS.md`, `USER.md`, `skills/`, `memory/`. Serves as the agent's working directory.

### Multi-Agent Orchestration

1. **Native Sub-Agents**: `sessions_spawn` (default runtime), sandboxable
2. **ACP External Agents**: `sessions_spawn` with `runtime: "acp"`, runs on host

## Claude Code Integration Possibilities

### Method 1: Direct ACP Spawn

```json
{
  "task": "Review this PR",
  "runtime": "acp",
  "agentId": "claude",
  "mode": "run"
}
```

### Method 2: Thread-Bound Session

```json
{
  "task": "Start coding session",
  "runtime": "acp",
  "agentId": "claude",
  "thread": true,
  "mode": "session"
}
```

### Method 3: Command-Line

```
/acp spawn claude --mode persistent --thread auto
```

### Required Configuration

```json5
{
  acp: {
    enabled: true,
    backend: "acpx",
    defaultAgent: "claude",
    allowedAgents: ["pi", "claude", "codex", "opencode", "gemini", "kimi"],
  }
}
```

Install plugin:
```bash
openclaw plugins install acpx
openclaw config set plugins.entries.acpx.enabled true
```

## Limitations

1. **Sandbox Incompatibility**: ACP runs on host, not sandboxed; requires non-sandboxed session to spawn
2. **Non-Interactive**: No TTY; requires explicit `permissionMode` configuration
3. **Thread Support**: Limited to Discord threads and Telegram topics
4. **Auth Restrictions**: Anthropic subscription usage outside Claude Code has been restricted historically
5. **Resource Limits**: Max 8 concurrent ACP sessions by default

---

## Recommendations

1. Install and enable `acpx` plugin
2. Configure `permissionMode: "approve-all"` for non-interactive use
3. Use thread binding for sustained conversations
4. Set Claude Code as default ACP agent
5. Spawn ACP from non-sandboxed sessions; use native sub-agents from sandboxed contexts

### Best Practices

- Create dedicated coding agents with appropriate workspaces
- Configure channel bindings to route coding tasks to ACP agents
- Use `/acp status` and `/acp sessions` for monitoring
- Set appropriate `runTimeoutSeconds` to prevent runaway sessions
- Use `cleanup: "delete"` for one-shot tasks
